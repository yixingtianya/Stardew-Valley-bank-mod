三、架构定稿：核心设计决策（不可推翻）

以下决策来自 V3.0，是开发中必须遵守的硬约束：

3.1 依赖纯洁性原则（最高优先级）

```
✅ 正确：Company → 传入 CompanyStatus → Interest
❌ 错误：Interest → 反向调用 ICompanyManager 获取状态
```

· IInterestCalculator.CalculateDepositRate 必须接收 CompanyStatus status 参数
· FixedCompanyInterestStrategy 和 DynamicCompanyInterestStrategy 实现此接口
· 严禁 Interest 模块内部调用 ICompanyManager

3.2 复利冷却机制

· 动态公司复利到期后，进入 112 天冷却期（一个完整星露谷年）
· 冷却期内强制单利结算
· 公司倒闭后重生，冷却期仍继续计时
· 此逻辑在 ICompanyManager 中管理冷却状态，在 IInterestCalculator 中执行冷却判定

3.3 状态乘数体系

公司状态 利率乘数 存款上限修正
繁荣期 (>150%) ×1.2 基础×2 + 20%
稳定期 (80%-150%) ×0.9 基础×2
饥饿期 (30%-80%) ×0.7 半锁（50%）
濒死期 (<30%) ×0.4 清空（0）

3.4 存款上限多元决定

IDepositLimitProvider 必须显式依赖 ICompanyManager 获取状态，应用所有修正因子。

3.5 作物倒闭冷却封锁【V3.8 修正】

· 公司倒闭后，同作物在当前季节（同一季节实例）内无法重新生成
· 跨季自动解除冷却（如春季倒闭→夏季即可重新生成）
· ICompanyManager.IsCropOnBankruptcyCooldown(cropId) 在公司生成前置校验中被调用

3.6 【V3.1 补完】等效支出公式（动态公司利率锚定）

动态公司基础日利率必须锚定作物的真实经济回报，公式如下：

```
等效支出 = 作物售价 ÷ 出种率 × 单次出种数
基础日利率 R = 日收益 ÷ 等效支出
```

存款利率衰减规则（V3.5 patch5 修正）：

R 区间 存款利率计算 贷款日利率
R > 20% 存款利率 = R × 0.5 R × 0.75
0% < R ≤ 20% 存款利率 = R（不衰减） R × 1.5
R ≤ 0% 存款利率 = 0%（钳位） 0%（钳位）

· 贷款利率硬下限 +1%。
· 存贷差始终大于 50%，无套利空间。
· GMCM 已实现主动拦截：滑动条实时钳制（存≤贷）+ 保存时拒绝写入（非法值不写盘、恢复旧配置、醒目红字报错）。
· 加工品不计入等效支出计算。

3.7 【V3.1 补完】新公司保护期

· 动态公司生成后，进入 14 天保护期
· 保护期内：豁免所有倒闭条件检测（连续无出货、利率持续为负、存款枯竭均不触发）
· 保护期内：利率计算正常执行，可存款/取款/借款
· 保护期结束后：正常参与每日倒闭条件检测

Fuel 模块职责定义【V3.1 新增】：

· 每日燃料需求计算：需求 = 种植总株数 × 基础维持系数 × 状态系数
· 基础维持系数：按作物类型配置（上古水果 0.15、啤酒花 0.8、蓝莓 0.3 等）
· 状态系数：繁荣×1.0、稳定×0.8、饥饿×0.5、濒死×0.3
· 燃料满足率：满足率 = 当日实际供应数 ÷ 需求数
· 公司状态判定：根据满足率区间映射对应状态
· 过渡期策略：季节过渡期内使用专用计算逻辑

```csharp
// 【V3.1】动态公司基础利率必须锚定等效支出公式
decimal equivalentCost = cropSellPrice / reseedRate × seedsPerHarvest;
decimal baseDailyRate = dailyProfit / equivalentCost;

// 存款利率衰减规则（V3.5 patch5 修正：移除线性衰减）
decimal depositRate = baseDailyRate switch
{
    > 0.20m => baseDailyRate × 0.5m,
    > 0     => baseDailyRate,         // 0% < R ≤ 20%: 不打折
    _       => 0                      // R ≤ 0%: 钳位
};

// 贷款利率规则（V3.5 patch5 修正）
decimal loanRate = baseDailyRate switch
{
    > 0.20m => baseDailyRate × 0.75m,
    > 0     => baseDailyRate × 1.5m,  // 0% < R ≤ 20%: 贷款上浮
    _       => 0                      // R ≤ 0%: 钳位
};
loanRate = Math.Max(0.01m, loanRate); // 硬下限 +1%
```

补丁一：公司生成上限与冷却校验接口

问题

V3.1 中 ICompanyManager 缺少查询“本季已生成公司数量”以及综合校验“是否允许生成新公司”的接口，导致开发者可能忽略单季新增上限（2个）和总席位上限（4个）。

新增接口

在 ICompanyManager 末尾追加：

```csharp
/// <summary>
/// 检查当前季节是否还能生成新的动态公司。
/// 规则：总活跃公司数 < 4 且 本季已生成数 < 2。
/// </summary>
bool CanSpawnNewCompanyInCurrentSeason();

/// <summary>
/// 尝试为指定作物生成新公司。
/// 内部会依次检查：
///   1. IsCropOnBankruptcyCooldown(cropId) → true 则返回 false
///   2. CanSpawnNewCompanyInCurrentSeason() → false 则返回 false
///   3. 已存在同作物公司 → 返回 false
///   4. 创始股本阈值是否达标 → 返回 false
/// 通过后创建公司并记录本季生成数。
/// </summary>
bool TrySpawnCompanyForCrop(CropId cropId);

/// <summary>
/// 当前季节已成功生成的公司数量（每日开始时重置为 0）
/// </summary>
int GetCurrentSeasonSpawnedCompanyCount();
```

实现约束

· OnDayStarted() 中，在检查新公司生成前，调用 TrySpawnCompanyForCrop 而非直接创建。
· 每日开始时，GetCurrentSeasonSpawnedCompanyCount() 必须重置为 0（由 OnDayStarted 负责）。
· 季度切换时，也重置该计数（已在 BeginSeasonTransition 中暗示，本补丁显式要求）。

补丁三：金融频道临时倒闭风险的应用接口

问题

IMessageScheduler 可提供 TemporaryBankruptcyRisk（如真消息时 50%），但 BankruptcyHandler 没有接收此值的接口，导致临时风险无法生效。

新增接口

在 IBankruptcyHandler 中追加：

```csharp
/// <summary>
/// 设置今日的临时倒闭风险乘数（覆盖正常风险计算）。
/// 例如：传入 0.5 表示今日倒闭概率强制为 50%（无论公司状态）。
/// 传入 null 表示取消临时覆盖，恢复标准计算。
/// </summary>
void SetTemporaryBankruptcyRiskOverride(decimal? riskOverride);
```

调用时序

在每日结算流程（V3.1 §五）的第 4 步之前（即倒闭检测前），由 MessageScheduler 调用：

```csharp
var news = messageScheduler.GetTodaysNews();
if (news.TemporaryBankruptcyRisk.HasValue)
    bankruptcyHandler.SetTemporaryBankruptcyRiskOverride(news.TemporaryBankruptcyRisk);
```

倒闭检测完成后（无论是否触发），当日结束时清除覆盖：SetTemporaryBankruptcyRiskOverride(null)。

补丁四：等效支出公式的作物类型区分

问题

等效支出公式要求“加工品不计入”，但 MarketContext 中没有体现当前计算针对的资产类型（种子/作物/加工品）。利率计算接口 CalculateDepositRate 无法判断。

修改 MarketContext 值对象

在 MarketContext 中增加属性：

```csharp
public enum AssetType
{
    RawCrop,        // 原始作物（用于利率计算）
    ArtisanGood,    // 加工品（不用于等效支出公式）
    Seed            // 种子（不用于利率锚定）
}

public class MarketContext
{
    // ... 原有属性 ...
    public AssetType AssetType { get; init; } = AssetType.RawCrop;
}
```

实现约束

在 DynamicCompanyInterestStrategy.CalculateDepositRate 中：

· 若 context.AssetType == AssetType.ArtisanGood 或 AssetType.Seed，则不使用等效支出公式，退回到固定默认利率（如 5%，可配置）。
· 仅在 AssetType == AssetType.RawCrop 时使用等效支出公式计算基础利率。

补丁五：保护期结束后状态迁移规则

问题

V3.1 状态机显示 Protected → Stable，但若保护期结束时满足率 >150%，理应进入 Prosperous 而非 Stable。

明确规则

1. 调用 FuelService.CalculateSatisfactionRate 获取当前满足率。
2. 根据满足率重新确定状态：
   · >150% → Prosperous
   · 80%~150% → Stable
   · 30%~80% → Hungry
   · <30% → Dying
3. 若新状态为 Dying，且是首次进入濒死，则进入 Restructuring（重组期）—— 注意：保护期结束后直接进入 Dying 是允许的，因为保护期只豁免倒闭检测，不豁免满足率下降。
4. 触发 StateChanged 事件。

修改 CompanyManager.OnDayStarted 中的保护期结束逻辑

伪代码示例：

```csharp
if (IsInProtectionPeriod(companyId) && protectionEndsToday)
{
    EndProtectionPeriod(companyId);
    var newStatus = DetermineCompanyStatusFromFuelSatisfaction(companyId);
    if (newStatus != CompanyStatus.Protected)
        SetStatus(companyId, newStatus);
}
```

补丁一：燃料库存机制重构（第三次修正）

对应漏洞：漏洞 #1
风险等级：🔴 致命（Critical）

【V3.8 修正】燃料判定方式 — 百分比满足率（替代 V3.2 绝对数量阶梯）

  实际实现采用百分比满足率判定，与架构重构报告 V2.0 一致，替代原 V3.2 设计的 Y 值绝对数量阶梯。

  满足率公式

  ```
  满足率 = FuelStock / (DBase × FPPerCrop)
  其中 FPPerCrop = 10，FuelStock 为 FP 整数
  ```

  状态判定（百分比制）

  ```
  满足率 > 150%     → Prosperous（繁荣期）
  满足率 80%-150%  → Stable（稳定期）
  满足率 30%-80%   → Hungry（饥饿期）
  满足率 < 30%     → Dying（濒死期）
  ```

  日消耗公式

  ```
  dailyConsumption = (int)(DBase × statusCoefficient × FPPerCrop)
  其中 statusCoefficient: Prosperous×1.0, Stable/New×0.8, Hungry×0.5, Dying/Protection×0.3
  ```

  新公司初始燃料

  ```
  FuelStock = Smax × 0.3 × FPPerCrop
  ```

  燃料=0 且状态为 Dying → 公司立即倒闭（Bankrupt），存款清零。

补丁一：GMCM 反射崩溃防护（Harmony Prefix）

1.1 问题根因

GMCM 1.12.0 的 Mod.OnUpdateTicking（订阅 SMAPI UpdateTicking 事件）每帧对 Game1.activeClickableMenu 进行反射：

  Helper.Reflection.GetField<bool>(activeClickableMenu, "titleInPosition", required: true)

SMAPI 的 Reflector.GetField<T> 使用 required: true，当：
  - activeClickableMenu 为 null → ArgumentNullException
  - 菜单对象没有 titleInPosition 字段（如 DialogueBox）→ InvalidOperationException

GMCM 的 ModConfigMenu..ctor() 在第 154 行同样对 SpecificModConfigMenu 进行此反射。

1.2 解决方案：GmcmSafetyPatch（Harmony Prefix）

在 GMCM 的两个入口点打 Harmony Prefix：
  - Mod.OnUpdateTicking — 每帧保护
  - ModConfigMenu..ctor() — 构造时保护

Prefix 逻辑：
  1. Game1.activeClickableMenu 为 null → return false（跳过 GMCM 原始处理）
  2. 菜单对象无 titleInPosition 字段 → return false
  3. 菜单有该字段 → return true（正常执行 GMCM 逻辑）

1.3 实现文件

文件：GmcmSafetyPatch.cs（独立于 BankMod.cs，职责单一）

关键设计决策：
  - 使用 AccessTools.TypeByName("GenericModConfigMenu.Mod") 优先加载，失败时 fallback 到 Assembly 遍历
  - 仅 Patch 已存在的方法，方法不存在时记录日志静默跳过
  - Prefix 方法本身零依赖（不引用 GMCM 类型），避免程序集加载失败
  - 对 ModConfigMenu..ctor() 的 Patch 使用相同 Prefix（同一检查逻辑）

1.4 接口约束

  GmcmSafetyPatch.Apply(IMonitor monitor)
    - 必须在 BankMod.Entry() 中最先调用（GMCM 注册之前）
    - monitor 用于日志输出
    - 失败静默：类型/方法未找到只记录 Warn 日志，不抛异常

补丁三：四步延迟保存拒绝机制

3.1 设计动机

GMCM 的 Save 回调在菜单上下文中运行，以下 UI 通道被 GMCM 菜单层阻塞：
  - HUDMessage / showRedMessage / chatBox.addErrorMessage → 被吞没
  - 直接 Game1.activeClickableMenu = new DialogueBox(...) → 被 GMCM 覆盖
  - Game1.exitActiveMenu() → 触发 emergencyShutDown()，破坏 UI mode stack

结论：Save 回调中不能直接操作菜单。

3.2 四步延迟序列

  Step 0 (Save 回调):
    HasIllegalConfig() → true
    → _config 回退为磁盘版本（Helper.ReadConfig）
    → _postSaveStep = 1
    → return（不写盘）

  Step 1 (下一帧 OnUpdateTicked):
    _postSaveStep == 1
    → Game1.activeClickableMenu = null（干净关闭，不调 exitActiveMenu）
    → _postSaveStep = 2

  Step 2 (再下一帧 OnUpdateTicked):
    _postSaveStep == 2
    → Game1.activeClickableMenu = new SafeDialogueBox(msg)
    → _postSaveStep = 3

  Step 3 (玩家关闭对话框 → OnMenuChanged):
    e.OldMenu is SafeDialogueBox && e.NewMenu is null
    → _postSaveStep = 4

  Step 4 (下一帧 OnUpdateTicked):
    _postSaveStep == 4
    → _gmcmApi.OpenModMenu(ModManifest)  // 重新打开 GMCM
    → _postSaveStep = 0（复位）

3.3 关键约束

  - 延迟步骤必须放在 OnUpdateTicked 的最顶端（Context.IsWorldReady 检查之前），因为 GMCM 打开时 Context.IsWorldReady 为 False
  - 同理，OnMenuChanged 中 SafeDialogueBox 关闭检测也必须放在最顶端
  - 使用 activeClickableMenu = null 而非 exitActiveMenu()，避免 UI mode stack 损坏
  - GMCM 重新打开必须延迟一帧（从 OnMenuChanged 只设标志，在 OnUpdateTicked 真正调用 OpenModMenu），避免事件处理器内的重入

补丁四：跨公司套利保护规则

4.1 校验范围

仅 Joja + 皮埃尔两个固定公司（_config.Companies[0] 和 [1]）。

4.2 校验公式

所有贷款利率 >= 所有存款利率，即 4 个条件：

  Joja.LoanRate >= Joja.DepositRate
  Joja.LoanRate >= Pierre.DepositRate
  Pierre.LoanRate >= Joja.DepositRate
  Pierre.LoanRate >= Pierre.DepositRate

4.3 触发时机

  - 启动时（ValidateAndFixConfigOnStartup）：自动修正并写盘
  - GMCM 滑块拖动时：实时显示一句话警告（通过 AddParagraph 的 Func<string> 每帧重算）
  - GMCM 保存时：拒绝写盘 + 触发四步延迟序列

4.4 setValue 不做钳制

  - GMCM 不实时反馈钳制结果，玩家拖到边界时滑块视觉不动会认为是 Bug
  - 在保存时检测并拒绝更符合玩家心智模型

补丁一：联机模式主机权威机制（§1.1-1.5）

1.1 核心原则：主机权威（Host Authority）

· 所有金融操作（存取款、借款、还款、日结算）只在主机端执行。
· 客机端的操作必须通过消息协议发送给主机，由主机鉴权并执行后广播结果。
· 客机端不直接修改任何金融数据。

1.2 主/客机判断

使用 SMAPI 内置 API：Context.IsMainPlayer
· 主机（Host）：true — 执行全部金融逻辑
· 客机（Client）：false — 仅执行 UI 交互，金融操作通过消息转发

1.3 事件注册

在 ModEntry.cs 的 Entry() 方法中注册：
· helper.Events.Multiplayer.PeerConnected += OnPeerConnected;
· helper.Events.Multiplayer.ModMessageReceived += OnModMessageReceived;

1.4 消息类型定义

消息类型常量字符串：
· "ConfigSync" — 主机向客机同步 ModConfig
· "BankOperation" — 客机向主机发送金融操作请求
· "BankDataSync" — 主机向全体客机广播银行数据更新
· "BankSnapshot" — 主机日结算后向全体客机广播完整快照

消息类标记 [Serializable]，包含：
· BankOperationRequest：操作类型（存款/取款/借款/还款）、公司名、金额、发起玩家ID
· BankDataSync：所有公司利率、状态、目标玩家自己的余额（不泄露他人隐私）

1.5 客机 OnDayStarted 跳过

· 客机端 OnDayStarted 中，若 !Context.IsMainPlayer，立即 return。
· 客机不执行任何日结算逻辑（利息计算、贷款扣息、公司倒闭检测等）。
· 客机的 UI 刷新通过接收主机 BankSnapshot 消息驱动。

补丁二：联机数据一致性保障机制（§2.1-2.4）

2.1 操作锁机制

· 主机端维护 Dictionary<long, bool>（玩家ID → 操作进行中）防止同一玩家并发操作。
· 操作开始前加锁，操作完成/超时后解锁。
· 客机操作超时时间：5 秒（可配置）。

2.2 数据同步时机

· 每次金融操作完成后立即广播 BankDataSync 给全体客机。
· 每日结算完成后广播 BankSnapshot（全量快照）。
· 客机加入时（PeerConnected），主机发送 ConfigSync + BankDataSync。

2.3 客机功能白名单

允许（需消息转发）：
· 存款、取款、借款、还款（通过 BankOperation 消息）

禁止：
· 直接修改任何金融数据
· 执行日结算
· 修改 GMCM 配置（仅主机可修改）

2.4 分家/合家存款模式（勘误六）

· 未分家（useSeparateWallets == false）：共同账户，所有玩家看到同一余额。
· 分家当天：执行 SplitBankAccountsAmongPlayers()，存款/贷款/利息按人数均分。
· 分家后（useSeparateWallets == true）：独立账户，按 playerId 隔离。
· 贷款跟随存款一起平分，还款周期/下次还款日保持不变。
· 分家当天金融操作按钮灰掉，直到日结算完成。

一、核心修正摘要

旧规则：饥饿期取款冻结，濒死期取款冻结，注资救市允许无额度限制。
新规则：取款改为限制取款（≤ 公司资产池余额），饥饿期禁止注资，濒死期入股救市翻倍回报。

二、资产池机制

定义：
· 有效贷款上限 = 原始贷款上限 × 状态乘数
· 资产池 = 有效贷款上限 − 已贷出未归还本金总额
· 玩家最大取款额 = min(该玩家存款余额, max(0, 公司当前资产池余额))

状态乘数：
· 繁荣期/稳定期：贷款上限乘数 ×1.0（基准不变）
· 饥饿期：贷款上限乘数 ×0.6
· 濒死期：贷款上限乘数 ×0.3

三、入股救市规则

· 可用阶段：仅濒死期（7天重组期）
· 注资上限：公司原始贷款上限 × 50%（不受状态乘数影响）
· 回报方式：公司复活后，注资金额翻倍计入该玩家的存款本金
· 回报生效条件：公司燃料满足率在7天内回升至 ≥ 30%
· 失败处理：公司倒闭，注资金额与存款一并清零
· 利率即分红：翻倍后的存款本金享受公司利率

四、复活后稳定性

· 公司脱离濒死后，燃料满足率重置为 100%（稳定期中部）
· 公司状态为稳定期
· 有效贷款上限恢复为原始贷款上限 × 1.0
· 资产池同步恢复

架构 V3.3.2 增量补丁（公司倒闭存款返还机制）

补丁版本：V3.3.2
补丁类型：机制新增 + 配置扩展
依赖：V3.3.1（公司状态操作限制重构）

一、核心规则

公司倒闭时，根据倒闭时公司所处的状态，按比例返还存款本金。
返还仅针对存款本金，不包括已计入的利息（利息在倒闭时归零）。

返还比例阶梯：

倒闭时状态 返还比例 设计逻辑
繁荣期 80% 产能过剩倒闭，玩家是超额供给的功臣
稳定期 50% 随机概率倒闭，玩家正常经营
饥饿期 0% 供给不足致死，有充足预警且可取款割肉
濒死期 0% 7天窗口+入股救市均未能挽回

二、不可逆阶梯校验

核心原则：繁荣期返还比例 ≥ 稳定期返还比例 ≥ 饥饿期返还比例（0%）

· 稳定期返还比例 = min(稳定期返还比例, 繁荣期返还比例)
· 饥饿期和濒死期固定为 0%，不接受任何配置

三、配置参数追加至 §10

参数 默认值 允许范围 说明
繁荣期倒闭返还比例 80% 0% ~ 100% 产能过剩死亡返还
稳定期倒闭返还比例 50% 0% ~ 100% 随机概率死亡返还
饥饿期倒闭返还比例 0% 固定0% 供给不足致死，不可调
濒死期倒闭返还比例 0% 固定0% 重组失败，不可调

GMCM 配置：
· 仅暴露"繁荣期倒闭返还比例"和"稳定期倒闭返还比例"两个滑块

· 滑块说明文字："稳定期返还比例不可超过繁荣期"

勘误六：联机财产分配与存款分割机制

问题来源：
原版星露谷在刘易斯家中的"财产分配"功能，会将联机存档中的共同现金按玩家数量分割为个人独立现金。如果银行存款不跟随分割，会出现问题：
1. 不分家时，存款按 ID 独立会让金融信息不透明。
2. 分家后，如果银行存款继续保持"共同状态"，会导致资金归属混乱。

修正方案：

1. 不分家时的存款模式：共同账户
· useSeparateWallets == false 时，所有玩家的银行存款是共同账户。
· 任何玩家的存入/取款操作都直接影响共同账户。
· UI 上显示"家庭存款"或"农场存款"。

2. 分家时：存款按人数均分
· 共同账户中的各项余额（存款本金、贷款本金、累计利息等）按在线玩家数量均分。
· 写入各自的 modData 独立账户。

3. 分家后：存款独立账户
· useSeparateWallets == true 时，每个玩家的银行存款完全独立。
· UI 只显示本玩家的存款数据。

4. 核心实现接口

SplitBankAccountsAmongPlayers() 方法逻辑：
· 获取在线玩家数量
· 对每个公司的共同存款/贷款/利息执行均分
· 余数归主机（保证总金额守恒）
· 继承原贷款合同条款（还款日、还款周期、日利率）
· 分家当天金融操作按钮灰掉，直到日结算完成

5. 贷款跟随存款平分
· 贷款必须与存款一起平分，没有自由选择模式。
· 拆分后的贷款，每人的还款周期、下次还款日保持不变。
· 拆分后，每人独立负责自己的那份贷款。

6. 反作弊说明
· 分家前，任何玩家操作共同账户都是合法的。
· 分家执行的代码在主机端运行，客机无权干预。
· 分家结果通过 BankDataSync 广播给客机。

7. 新增约束
· 共同账户模式：useSeparateWallets == false 时共享
· 分家均分：状态变化当日执行等额均分
· 余数归主机：保证总金额守恒
· 分家后独立：modData 独立存储
· 操作锁：分家当天金融操作暂停

补丁二：利率折扣规则（最终版，V3.5 patch5 修正）

原线性衰减公式在 10%–20% 区间内导数非正，导致高 R 作物存款利率反而低于低 R 作物。现彻底简化：

| R 区间 | 存款利率 | 贷款利率 |
|---|---|---|
| **R > 20%** | **R × 0.5** | R × 0.75 |
| **0% < R ≤ 20%** | **R（不打折）** | **R × 1.5** |
| **R ≤ 0%** | **0%（钳位）** | **0%** |

附加约束：
- 贷款利率硬下限 **+1%**（即使 R≤0% 时钳位为 0，实现中确保不低于 1%）。
- 固定公司（皮埃尔、Joja）不适用上述折扣规则，其利率始终从 config 读取（单利锁定）。
- 实现位置：`IInterestCalculator` 的 `CalculateDepositRate` / `CalculateLoanRate` 方法，在利率钳位阶段执行。

补丁三：计算方法（统一标准）

等效支出：
· 有商店种子的作物：等效支出 = 种子购买价
· 无商店种子的作物（`*`标记）：等效支出 = 作物售价 ÷ 种子制造机平均出种率（≈2）

等效日收益（连续经营稳态模型）：
· 单次收获作物：等效日收益 =（售价 − 等效支出）÷ 生长天数
· 连续收获作物：等效日收益 =（单次收获售价 − 等效支出÷全周期收获次数）÷ 再收天数
  全周期取作物在室外可跨越的总天数（单季28天，跨两季56天，跨三季84天）

基础日利率 R：R = 等效日收益 ÷ 等效支出

燃料参数（与 V3.2 一致）：
· Y = 单土地月产能（个/月/株）
· D_base = (5/3) × Y（基础日消耗，个/天）
· Smax = Y × 10（仓库上限）

补丁十一：V3.7 手动复利检测 + 利息硬顶 + 资产池修正 + UI 优化（2026-05-04）

一、手动复利检测机制（patch!!!.txt 核心内容）

  问题：玩家每日将产生的利息取出后存回同一公司，使本金呈日复利增长。
  严重性：不需任何资源投入即可指数爆炸，破坏所有其他金融机制。

  检测算法（7天滑动窗口 + 峰值突破）：
  1. 每日计算本金增量 delta = BaseAmount - PreviousBaseAmount
  2. 正值写入 RecentPrincipalDeltas[7] 滚动窗口
  3. 从旧到新扫描窗口内所有正增量：
     - 未触发"第一次变大"：跳过未变大的增量，直到 delta > 最近正增量 → 触发，记录峰值，计数=1
     - 已触发后：delta > 当前峰值 → 刷新峰值，计数+1
  4. 窗口内峰值突破累计 ≥ 3 次 → 标记惩罚（7天，存款利率 ×0.10）
  5. 窗口每 7 天重置状态
  6. 惩罚期剩余天数逐日递减

  设计原则：
  - 不追踪资金来源，只看本金增量是否持续变大
  - 不限制存取款
  - 不跨公司比对
  - 不预设基准（杠杆不会自动成为护身符）
  - 仅影响存款利率，贷款利率不受影响

  实现位置：
  - CompanyManager.DetectManualCompoundInterest() — 在 SettleDailyInterest 之后调用
  - InterestCalculationContext.IsPenaltyPeriod — 传递给利率策略
  - CompanyAccount 新增 8 个字段：RecentPrincipalDeltas[7], WindowDayIndex, HasFirstIncrease,
    LastPositiveDelta, WindowPeak, WindowBreakCount, PenaltyDaysRemaining, PreviousBaseAmount
  - Fixed/Dynamic 利率策略：计算末端 ×0.10 if IsPenaltyPeriod
  - BankMenu.BuildContext: 传递 IsPenaltyPeriod

二、复利公式根因修复

  问题：UseCompoundInterest=true 时利息按 DepositBalance（含累计利息）计算 → 利滚利。
  修复：利息始终按 BaseAmount（本金）计算，删除 UseCompoundInterest 分支。

  公式变更：
    之前：interest = UseCompoundInterest ? DepositBalance * rate : BaseAmount * rate
    现在：interest = BaseAmount * rate

三、利息不可突破存款上限

  问题：利息叠加可使 DepositBalance 超过 DepositLimit。
  修复三层面防御：
  1. 计息基数钳位：interestBase = min(BaseAmount, DepositLimit)
  2. 利息入账截断：若 DepositBalance + interest > DepositLimit，裁掉超出部分
  3. AccInt 只记录实际入账部分（被裁掉的利息不计入累计）

四、BaseAmount 负值安全重置

  问题：取款时 BaseAmount = max(0, BaseAmount - amount) 钳到 0，但 AccumulatedInterest 不随之减少。
  当 AccInt > DepositBalance 时，BaseAmount 计算为负值 → 钳到 0 → 利息为 0。
  修复：SettleDailyInterest 中，若 BaseAmount ≤ 0 且 DepositBalance > 0，
        重置 AccInt=0, BaseAmount=DepositBalance, PreviousBaseAmount=BaseAmount。

五、资产池规则修正

  问题：固定公司也有资产池概念，且动态公司所有状态都依赖资产池。
  修复：
  - 固定公司：取款上限 = DepositBalance（无资产池限制）
  - 动态公司 Stable/Prosperous/New/Protection：同上，无限制
  - 动态公司 Hungry：资产池 = LoanLimit × 0.6 - 未还本金
  - 动态公司 Dying：资产池 = LoanLimit × 0.3 - 未还本金

六、NumberInputMenu 全部按钮激活

  NumberInputMenu 已有 FormatWithCommas（逗号格式化）、首数字0无效、FillMax 等功能，

V3.10 阶段八补丁（2026-05-14）：利息欠债、本金欠债、破产保护

一、每日结算流程修正

实际流程（阶段八完成后）：
1. 适配器捕获时间/天气/运气
2. FuelService 更新库存与满足率 → 判定公司状态
3. 新公司保护期内跳过倒闭检测
4. CompanyManager 检测倒闭条件（燃料=0 → 立即倒闭，清零出售计数）
5. InterestCalculator 计算存款日利率
6. 动态公司贷款：每日从现金扣息（现金不足→逾期欠息→利息欠债）
   固定公司贷款：利息累积到到期日
7. 到期检测：现金够→自动还款；不够→宽限期
8. 宽限期结束：强制划扣(现金+低利率存款优先)
   划扣不够→贷款冻结(IsFrozen)+进入破产
9. 结算存款利息（破产期间照常）
10. 手动复利检测
11. 持久化

★ 与原设计的关键差异：
  - 破产不在每日管线检测，而是在强制划扣失败时触发
  - 破产后存款利息照常计算（不冻结）
  - 破产只禁止借款，不禁止取款/存款
  - 逾期不禁止借款（只有破产禁借）

二、破产保护规则（最终版）

触发：宽限期结束→强制划扣(现金+全部存款)→仍不够还→贷款冻结+进入破产

冻结贷款行为：
  - 不计息（DailyTick 跳过 IsFrozen 贷款）
  - 无到期日
  - 不扣罚息
  - 累计利息和逾期欠息保留不清零
  - 手动还款可结清

破产期间影响：
  1. 禁止借款（LoanService.IssueLoan 拦截）
  2. 日间收入追踪（OnUpdateTicked 每帧比较金钱快照，增量×50%扣款偿债）
  3. 过夜出货收入扣款（DayEnding 快照→DayStarted 比较→×50%扣款）
  4. 取款/借款豁免扣款（ExemptNextMoneyIncrease 标记）
  5. 右下角常驻标语

退出破产：所有冻结贷款还清→标志位清零→弹出"恭喜，享受你的春天吧"

三、贷款独立化

- IssueLoan 取消加贷合并，每笔借款独立 LoanRecord
- 同日、同公司、同周期 → 合并（利率加权平均）
- 不同日 → 各自独立到期日
- 逾期部分还款不重置到期日
- UI 新增"明细/摘要"切换 + 滚动列表(每屏2条) + 逐条还款按钮

四、偿债优先级

  1. 冻结贷款（破产债务）
  2. 动态公司贷款 — 剩余天数最少
  3. 动态公司贷款 — 本金最高
  4. 按作物 ID 字母序
  5. 固定公司贷款排最后
每笔贷款内部：逾期欠息 → 累计利息 → 本金

  PeerConnected：
    主机 -> 构造ConfigSyncMessage -> SendMessage(MsgConfigSync, targetPeer)

    1. 检查操作锁(_operationLocks[req.SenderId])

    4. 释放操作锁

    主机 -> 构造BankSnapshot(所有公司状态+余额) -> SendMessage(MsgBankSnapshot)

  Dictionary<long, bool> _operationLocks

    - 不阻止原版交互（不 return false）
    - ShouldInjectDialogue 检查条件（不修改状态）
    - 有对话时设 Game1.afterDialogues，原版对话播完后再播 mod 对话

  ShouldInjectDialogue 逻辑：
    - 破产状态：按好感度档位判定，跨档位防重复
    - 欠债状态：15% 随机触发，同日同 NPC 不重复
    - 配偶检查：isPartner = spouse || isRoommate
      配偶破产 → 无档位、单次触发、专属赠礼
      配偶欠债 → 无随机（始终触发）

  TryBankruptcyDialogue：
    - 普通 NPC：hearts ≥ 8 触发 GiveGift（30+ NPC 赠礼表）
    - 配偶：始终赠礼，Shane 特殊处理（披萨 206 + 啤酒 346 双赠礼）

10.3 还清祝贺流程

  破产退出检测（OnUpdateTicked）：
    _lastBankruptcyState=true && !account.IsInBankruptcy → "恭喜，享受你的春天吧！"
    → TryCongratulate(account) → DebtClearedCongratsShown=true
    → 随后 NPC 对话触发 afterDialogues → GetCongratsLine → MarkCongratsSpoken

10.4 数据模型新增字段（BankAccountData）

  DebtNpcSpoken          : List<string>  欠债对话已触发标记（"debt_NPC_day"）
  BankruptcyNpcGifted    : List<string>  破产赠礼已触发标记（"bankrupt_NPC_tier"/"bankrupt_NPC_spouse"）
  CongratsNpcSpoken      : List<string>  祝贺对话已触发标记（NPC 名）
  DebtClearedCongratsShown : bool        是否进入祝贺阶段

10.5 本阶段 Bug 修复

  Bug 1 — 祝贺对话不播放：
    原因：afterDialogues 回调中 MarkCongratsSpoken 先于 GetCongratsLine 执行，
          MarkCongratsSpoken 将 NPC 加入 CongratsNpcSpoken 列表，
          GetCongratsLine 检查列表发现 NPC 已在其中 → 返回 null → 对话永不播放
    修复：交换顺序 — 先 GetCongratsLine 获取文本，再 MarkCongratsSpoken 标记

  Bug 2 — Morris 事件后 Joja 收银员不显示购买/出售选择框：
    原因：商店拦截守卫仅检查 CompletedRoute（Joja/CC 路线完成），
          但 Morris 供应架事件独立于路线完成，_morrisEventSeen 无法通过守卫
    修复：守卫条件改为 if (string.IsNullOrEmpty(CompletedRoute) && !_morrisEventSeen) return;

  Bug 3 — Shane 配偶破产赠礼名称错误：
    原因：SpouseLines.GetBankrupt 中 Shane 条目 giftName 写为 "披萨+啤酒"，
          但 GetBankrupt 返回单物品元组，且 TryBankruptcyDialogue 已做 Shane 双赠礼特殊处理
    修复：giftName 改为 "披萨"，双赠礼逻辑在 TryBankruptcyDialogue 中保持不变
