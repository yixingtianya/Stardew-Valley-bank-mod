一、项目概述

Dynamic Financial System 是星露谷物语 1.6 的经济扩展模组，为游戏引入了手机银行、
动态公司诞生与倒闭、利率浮动市场、破产保护、NPC 财务状态对话、电视金融频道等
完整金融模拟系统。Mod 完全基于 SMAPI 4.0 官方 API，零外部 NuGet 依赖。

这个项目的特殊性在于：全部代码在 AI 辅助下完成，但决策权始终在人手中。

三、AI 协作模式：逻辑仲裁与三方验证闭环

本项目采用了一套独创的 AI 协作方法论——"逻辑仲裁与三方验证闭环"
（Logic Arbiter & Tri-Verification Loop，详见 人机协作.txt），
从根本上解决了单体 AI 在复杂软件工程中的三类核心失效模式：

  1. 逻辑盲猜 — AI 在信息不足时基于概率生成假设而非声明未知
  2. 逻辑打转 — AI 在前置条件缺失时反复尝试无效操作
  3. 表面完成 — AI 为满足"完成"指令采用脆弱方案强行绕过障碍

3.1 系统角色

  系统由四个严格分离的角色构成：

  角色              职责                              约束
  ────────────────  ────────────────────────────────  ──────────────────
  逻辑仲裁者(我)     需求逻辑唯一持有者、质疑提炼者、    不参与代码实现
                    任务调度者、逻辑前提保障者
  架构/代码AI        根据明确需求和约束生成架构方案      仅在清晰定义的逻辑
  (Claude Code)      或代码实现（增量补丁形式）          边界内工作
  多方验证AI         以独立新会话为载体，对给定需求和     仅找逻辑漏洞，
  (DeepSeek)         架构进行逻辑矛盾攻击                不提供修正方案
  认知翻译AI         将代码AI的复杂方案或报错翻译成      不评价方案好坏，
                    逻辑仲裁者可理解的"行为逻辑"        只解释"它在做什么"

3.2 核心工作流

  协议A（生成）→ 协议B（质疑提炼与多方分发）→ 协议C（饱和式共识终结）
  → 协议D（认知翻译与障碍识别）→ 协议E（逻辑障碍清除与基线冻结）
  → 协议F（增量归档）

  关键创新：验证的终点不是"找到真理"，而是达到"多方沉默"状态——
  当所有独立验证 AI 实例均回复"无有效反驳点"时，验证终止。

四、技术架构决策

4.1 架构分层

  Domain/             值对象、枚举（零依赖）
  Services/Abstractions/  接口定义（仅依赖 Domain + Data）
  Services/Core/      业务逻辑实现（依赖 Abstractions）
  UI/                  表现层（依赖 Services.Abstractions + Services.Core）
  Patches/             Harmony 补丁（仅 TV + NPC 两处，最小化原则）
  Messages/            多人模式消息协议

4.2 核心设计模式

  · 策略模式 — IInterestCalculator 双实现：FixedCompany + DynamicCompany
  · 手动 DI — ModServices 聚合对象，构造函数注入，无框架依赖
  · 桩模式 — 5 个计划中接口均有桩实现，返回安全默认值
  · Repository 模式 — BankAccountService 封装 JSON 序列化与内存缓存
  · Harmony Prefix — 最小化 Monkey Patch，仅 3 处，避免污染游戏运行时

4.3 关键工程决策

  · 持久化安全：所有写入方法接收 BankAccountData 参数，由调用方统一 Load/Save，
    消除"服务内部 Save → 调用方保存 stale 副本覆盖"类 Bug（本项目最严重 Bug 模式）

  · 存档隔离：WriteSaveData/ReadSaveData（SMAPI per-save API）替代 WriteJsonFile
    （mod-global），消除跨存档数据污染

  · 内存缓存：BankAccountService.Load() 缓存 JSON 反序列化结果，
    InvalidateCache() 在存档加载时清缓存，消除重复 I/O

  · 事件驱动：SMAPI 标准事件（SaveLoaded/DayStarted/UpdateTicked/DayEnding/
    MenuChanged/Warped/Saving/AssetRequested 等）+ 最小化反射（仅 Morris 隐藏/
    TV currentChannel/FBN screen 三处）

  · 跨公司套利保护：GMCM 四步延迟保存拒绝机制，非法配置不写盘

五、AI 协作中的关键挑战与解决

5.1 持久化覆盖模式（V3.6 最严重 Bug）

  现象：燃料库存每天归零。根因：FuelService 内部 Load → 修改 → Save，
  然后 CompanyManager 随后 Save stale 副本，覆盖了 FuelService 的变更。
  AI 最初给出的修复是"在 FuelService 里再 Save 一次"——这是"表面完成"的典型案例。
  通过协议D（认知翻译）识别出问题本质是"多个写入者竞争同一持久化对象"，
  然后通过协议E固定基线："所有写入方法接收 BankAccountData 参数，调用方统一 Save"。

5.2 SMAPI 合规性偏差

  AI 多次使用猜测的游戏事件 ID 格式（Game1.CurrentEvent.id.Contains("502261")）
  和未文档化的反射访问（characterDialogue 字段）。通过协议B分发给 DeepSeek 验证后，
  确认这些 API 依赖未经 SMAPI 文档支持。随后引入 RouteService 层，
  统一使用 eventsSeen（SMAPI 标准 API）+ mail fallback 进行路线检测。

5.3 跨存档状态污染

  _config.Companies 是全局单例，AI 的路线改名是 in-place 修改，导致前一个存档的
  公司名残留在下一个存档。AI 最初没有意识到这个问题（逻辑盲猜——它假设
  每次加载存档都会重新创建 config 对象）。通过协议B多方验证发现后，
  引入三重防护：磁盘 config.json 读取原始名 → 恢复全部 → 再按存档状态改名。

5.4 NPC 对话顺序 Bug

  afterDialogues 回调中 MarkCongratsSpoken 先于 GetCongratsLine 执行，
  导致对话文本永远为 null。这是 AI 在"完成任务"时没有考虑副作用的典型案例——
  它知道需要"标记已对话"和"获取对话文本"两件事，但没考虑顺序依赖。
  这种 Bug 类型是协议D（认知翻译）设计用来识别的核心模式之一。

六、人机分工

  人（逻辑仲裁者）的工作：
  ┌─────────────────────────────────────────────────────────────┐
  │ · 需求定义：demand.txt 15 个阶段的完整需求逻辑              │
  │ · 内容创作：TV.txt / dialog.txt~dialog4.txt / Crops values  │
  │ ·           所有 NPC 对话文本、金融频道脚本、作物数据        │
  │ · 逻辑仲裁：当 AI 出现逻辑矛盾时，提炼质疑、分发验证、      │
  │            亲自介入解决前提缺失                               │
  │ · 架构审查：审核增量补丁的逻辑自洽性（不审核代码正确性）    │
  │ · 最终签收：每个功能在游戏内实测验证                         │
  └─────────────────────────────────────────────────────────────┘

  AI（Claude Code + DeepSeek）的工作：
  ┌─────────────────────────────────────────────────────────────┐
  │ · 架构设计：将需求翻译为 C# 接口、类、方法签名              │
  │ · 代码生成：全部 .cs 源文件的编写                            │
  │ · Bug 修复：根据逻辑仲裁者提供的 Bug 描述定位并修复          │
  │ · 文档生成：架构总、重构报告、README、更新公告               │
  │ · 构建验证：dotnet build + 错误修复循环                      │
  └─────────────────────────────────────────────────────────────┘

  关键原则：AI 是"速度杠杆"，不是"决策替代"。所有架构决策、需求取舍、
  内容创作、逻辑审核均由人类完成。AI 负责将已确认的逻辑转化为代码，
  以及在人类发现问题后执行修复。

七、技术栈选择理由

  · Claude Code (Anthropic Claude Opus 4.7)：主力代码生成。
    优势：长上下文窗口（1M tokens），适合在单个会话中维护项目全局一致性；
    扩展思考模式（31,999 tokens），适合复杂架构推理和跨文件重构。

  · DeepSeek V4 Pro：多方验证AI。优势：独立运行的验证实例，
    不受 Claude Code 会话内的"思维惯性"影响，可提供真正独立的逻辑攻击。

  · C# / .NET 6.0 / SMAPI：星露谷物语 Mod 开发的唯一可行技术栈。
    选择 SMAPI 4.0+ 的 WriteSaveData/ReadSaveData API 而非 WriteJsonFile，
    是项目中期通过多方验证发现的关键架构修正。

八、结论

Dynamic Financial System 是一个验证"AI 是否可以用于复杂软件工程"的实验。
实验结果是：可以，但需要一套结构化的方法论来管理 AI 的认知局限。

"逻辑仲裁与三方验证闭环"不是一个自动化流水线——它的核心是人。
人在每一个逻辑死锁点介入，识别 AI 的盲猜、打转和表面完成，
然后注入新的前提条件，让 AI 在新基线上重启。

这个方法论的副产品是：最终的代码库几乎没有"因 AI 不理解需求而写的死代码"。
因为每一行代码在写入之前，其背后的逻辑前提都经过了多方验证。

项目完成时，15 个阶段、55 个文件、4800 行代码，0 个外部依赖，
0 个因"AI 幻觉"导致的功能偏差。所有偏差都是经过人类确认的设计取舍。
