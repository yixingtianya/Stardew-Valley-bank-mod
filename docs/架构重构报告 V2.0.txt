六、关键架构变更

  6.1 消除静态单例
    原代码：internal static BankMod? Instance（全局可变状态）
    重构后：ModServices 聚合对象，通过构造函数注入到 UI 组件
    优势：可测试、无全局状态、依赖关系显式化

  6.2 接口提取
    原代码：所有逻辑内联在 BankMod.cs（883行 Monolith）
    重构后：5 个核心接口 + 实现（IInterestCalculator, ICompanyManager,
            IDepositLimitProvider, IBankAccountService, IFuelService）
    优势：策略可替换、单元测试可行、符合开闭原则

  6.3 分层架构
    原代码：3 个平面命名空间（BankMod, BankMod.Data, BankMod.UI）
    重构后：4 层架构
      Domain/          — 值对象、枚举（零依赖）
      Services/Abstractions/ — 接口定义（仅依赖 Domain + Data）
      Services/Core/   — 业务逻辑实现（依赖 Abstractions）
      UI/              — 表现层（依赖 Services.Abstractions + Services.Core）
    优势：依赖方向内聚、新增功能只需实现接口

  6.4 利率计算策略化（Stage 6 完成双策略）
    原代码：BankMod.GetEffectiveDepositRate() static 方法
    重构后：IInterestCalculator 接口 + FixedCompanyInterestStrategy + DynamicCompanyInterestStrategy
    动态策略：V3.5 patch5 三段式折扣（R>20%×0.5, R<=20%不打折, 贷款硬下限+1%）
    选择逻辑：company.IsDynamic ? dynamic : fixed

  6.5 BankMod.cs 瘦身
    原代码：883 行（业务 + UI + GMCM + 事件）
    重构后：750 行（SMAPI 事件适配 + GMCM + 四步延迟 + 手机管理 + DayEnding）
    业务逻辑迁移：SettleDailyInterest -> CompanyManager
                  利率计算 -> FixedCompany/DynamicCompanyInterestStrategy
                  账户管理 -> BankAccountService
                  燃料管理 -> FuelService
                  出货追踪 -> ShipmentTrackingService
    新增：DayEnding 事件（出货箱处理 + 手机移除）、Phone Type=Quest

  6.6 桩模式（Stub Pattern）
    5 个"计划中"接口均有桩实现，返回安全默认值（0、false、空数组）。
    未来实现只需替换对应桩为真实实现，无需改动调用方代码。

  6.7 GMCM 反射安全层（Harmony Patch）
    问题：GMCM 1.12.0 每帧对 activeClickableMenu 反射 titleInPosition，DialogueBox 无此字段导致崩溃
    解决：GmcmSafetyPatch.cs — Harmony Prefix 补丁
    兜底：SafeDialogueBox（DialogueBox 子类 + public bool titleInPosition 字段）

  6.8 跨公司套利保护
    setValue 不做钳制，滑块完全自由
    保存时检测 4 条规则（所有 LoanRate >= 所有 DepositRate）
    非法时拒绝写盘 + 四步延迟序列

  6.9 燃料库存系统（Stage 6 新增）
    FP 整数化：1 标准作物 = 10 FP，内部 int，UI 层 /10 显示
    非对称规则：出货 +10/+20/+15 FP，购买/卖出 -5 FP
    日消耗：DBase * statusCoefficient * 10 FP
    状态驱动：满足率 = FuelStock / (DBase * 10)，4 级判定（>150%/80-150/30-80/<30）

  6.10 出货追踪与动态公司生成（Stage 6 新增）
    ShipmentTrackingService：DayEnding 扫描出货箱，35 条目 QID->CropCode 映射字典
    生成条件：累计出售量 >= 50 + 总席位 < 4 + 单季 < 2 + 无同作物 + 无冷却 + 非排除
    保护期：3 天（New 状态，不参与状态判定）
    倒闭冷却：当前季节（同一季节实例，跨季自动解除）【V3.8 修正】

  13.1 DepositLoanCoefficient 统一存款上限公式

    问题：存款上限与贷款上限之前分散为 6 个独立配置项（皮埃尔/Joja/低R/中R/高R 各一个
    DepositLimit 和 LoanLimit），数值之间没有逻辑关联，修改时容易产生矛盾配置。

    修复：新增统一配置项 DepositLoanCoefficient（默认值 5000），公式化计算：
      DepositLimit = cropCost × DepositLoanCoefficient
      贷款上限 = DepositLimit × 状态乘数（繁荣/稳定 ×1.0, 饥饿 ×0.6, 濒死 ×0.3）

    这使存款上限自动锚定作物经济价值，高价值作物（杨桃、上古）自动获得高存款上限，
    低价值作物（防风草、土豆）存款上限相应较低。玩家修改一个系数即可全局缩放。

    删除的旧配置项（6 个）：
      Pierre.DepositLimit, Pierre.LoanLimit, Joja.DepositLimit, Joja.LoanLimit,
      LowCropLoanLimit, MediumCropLoanLimit, HighCropLoanLimit

    GMCM 变更：

  13.2 存款上限 = 本金上限（利息不可突破）

    核心原则：存款上限是"本金上限"，而非"总余额上限"。累计利息可以让总余额超过
    存款上限，但玩家不能再主动存入超过上限的本金。

    规则细化：
    - 计息基数：interestBase = min(BaseAmount, DepositLimit)
    - 利息入账：若 DepositBalance + interest > DepositLimit，不截断利息（利息不受限）
    - 存款操作：maxDepositAmount = max(0, DepositLimit - BaseAmount)（仅本金受限）
    - BaseAmount 永远不会超过 DepositLimit

    这修正了 V3.7 中"利息硬顶"过度激进的问题——之前利息也被截断导致玩家在
    存款满额后完全没有利息增长。新规则下利息正常累积，只是不能主动存入更多本金。

    文件：CompanyManager.cs (SettleDailyInterest, 存款按钮限制)

  13.3 AccInt 安全重置（BaseAmount ≤ 0 场景）

    问题：取款钳 BaseAmount 到 0 但 AccInt 不减，AccInt > DepositBalance 时
    BaseAmount 计算为负值 → 钳到 0 → 利息为 0 → 死锁。

    修复：每日 SettleDailyInterest 中检测：
      if (BaseAmount ≤ 0 && DepositBalance > 0)
        → AccInt = 0, BaseAmount = DepositBalance, PreviousBaseAmount = BaseAmount

    效果：重置后公司回到干净状态，后续利息正常按本金计算。

    文件：CompanyManager.cs SettleDailyInterest

    3. 对每个售出的作物：Mapping QualifiedItemId → CropCode
    4. 调用 CompanyManager.ApplySuppression + FuelService.RecordExternalSale

    13.8.2 CropSuppressionData 模型

    新增数据模型（BankAccountData 内嵌类）：
    | 字段 | 类型 | 说明 |
    |------|------|------|
    | CropCode | string | 被打压的作物代码 |
    | Stacks | int | 当前打压层数（≤ SuppressMaxStacks） |
    | RemainingDays | int | 每层打压剩余天数 |

    持久化在 BankAccountData.CropSuppressions : List<CropSuppressionData>

    文件：Data/BankAccountData.cs

    13.8.3 ApplySuppression（CompanyManager）

    - 售卖数量 ≥ 50 → +3 层打压
    - 售卖数量 ≥ 20 → +2 层打压
    - 售卖数量 < 20 → +1 层打压
    - 层数上限 = SuppressMaxStacks（默认 3）
    - 每层持续天数 = SuppressEffectDurationDays（默认 5 天）
    - 同作物重复打压刷新 RemainingDays

    文件：CompanyManager.cs ApplySuppression

    13.8.4 每日打压衰减（TickSuppression）

    OnDayStarted 第 4.5 步：
    - 所有 CropSuppressions 的 RemainingDays 逐日递减
    - RemainingDays 归零 → Stacks -1
    - Stacks 归零 → 移除该条目

    文件：CompanyManager.cs TickSuppression

    13.8.5 打压对利率的影响

    在 DynamicCompanyInterestStrategy 中：
    - 打压层数 > 0 → 利率 -= min(Stacks × |SuppressMaxDropPerDay|, |SuppressMaxDropPerDay| × SuppressMaxStacks)
    - SuppressMaxDropPerDay（默认 -0.02，即每层 -2%/天）
    - 仅在动态公司利率计算中生效，固定公司不受影响

    文件：DynamicCompanyInterestStrategy.cs

  13.9 Stage 7 连续售卖加成与停售衰减

    13.9.1 连续售卖加成（7.1）

    利息计算上下文新增 ConsecutiveSellDays 字段。
    - 连续售卖 > 0 天：存款利率 + min(天数 × 每层加成, 加成上限)
    - ConsecutiveSellDepositBonusPerDay（默认 +0.5%/天）
    - ConsecutiveSellDepositBonusCap（默认 +5.0%）
    - 贷款同理使用 ConsecutiveSellLoanBonusPerDay / ConsecutiveSellLoanBonusCap（默认 +1.0%/天, +10.0%）

    13.9.2 停售衰减（7.2）

    - 连续售卖 = 0：存款利率 -= SellDecayDepositPerDay（默认 -0.5%/天）
    - 贷款：利率 -= SellDecayLoanPerDay（默认 -1.0%/天）
    - 衰减无下限（可持续变负，直到受 DepositRateFloor 约束）

    13.9.3 计算顺序（7.4）

    固定顺序确保所有因子可预测：
    base → +consecutive/decay → -suppression → ×luck → +weather → clamp → ×penalty(0.10)

    文件：FixedCompanyInterestStrategy.cs, DynamicCompanyInterestStrategy.cs, BankMenu.cs (BuildContext)

二十七、Bug 修复补丁（2026-05-29）：手机丢失检测 + 手机本地化 + 公司名回退

  27.1 Bug 1 — 手机丢失检测失败（跨日丢失无法补发）

  问题现象
    玩家将银行手机扔进垃圾桶后，第二天不会收到补发邮件。

  根因分析
    OnDayStarted 中手机丢失检测依赖两个 in-memory 布尔字段：
      _phoneSeenInInventory — 标记手机曾出现在背包
      _phonePutInChest — 标记手机被放入箱子
    这两个字段在每天 OnDayStarted 开始时被重置为 false。
    如果手机在昨天获得（flag="1"），今天 OnDayStarted 执行时：
      _phoneSeenInInventory = false（刚重置）
      → 条件 phoneFlag=="1" && _phoneSeenInInventory && !_phonePutInChest && !PlayerHasPhone()
      → 永远不会为 true
      → 手机丢失永远不会被检测到

  修复方案
    用 SMAPI 持久化存档存储（ReadSaveData/WriteSaveData）替代 in-memory 变量：
      - 新增存档键 "BankMod_PhoneInChest"（"1"=手机在箱子中，"0"=不在箱子）
      - OnInventoryChanged：
        e.Removed 包含手机 且 activeMenu 是 ItemGrabMenu → WriteSaveData("BankMod_PhoneInChest", "1")
        e.Added 包含手机 → WriteSaveData("BankMod_PhoneInChest", "0")
      - OnDayStarted：
        bool phoneInChest = ReadSaveData<string>("BankMod_PhoneInChest") == "1";
        if (phoneFlag=="1" && !phoneInChest && !PlayerHasPhone()) → 判定丢失 → 补发

  优势
    - 跨日持久化：即使游戏重启，箱子标记仍然保留
    - 不搜全图箱子，只追踪"手机是否在箱子"这一语义
    - 不误判光标拿起状态、不误判箱子存取

  删除字段
    - _phoneSeenInInventory（已被持久化存档键替代）
    - _phonePutInChest（已被持久化存档键替代）

  代码位置
    BankMod.cs OnDayStarted (~L982), OnInventoryChanged (~L1293, L1302)

  27.2 Bug 2 — 手机名称在中文版显示英文（Data/Objects 本地化）

  问题现象
    手机物品在中文游戏版本中显示英文名称 "Cell Phone"，而非中文 "手机"。

  根因分析
    OnAssetRequested 中 Data/Objects 注入使用 I18n.Get("mod.27") 设置 DisplayName：
      DisplayName = I18n.Get("mod.27")  // 可能返回默认语言值
    I18n.Get() 在 AssetRequested 事件中可能因资产缓存机制返回默认语言值，
    导致 DisplayName 被缓存为英文，后续语言切换无法更新。

  修复方案
    使用 SDV 1.6 的 [LocalizedText] 令牌语法，让游戏自身的 TokenParser 动态解析本地化文本：

    1. Data/Objects 注入改为令牌引用：
       DisplayName = "[LocalizedText Strings\\Objects:BankMod.Phone]"
       Description = "[LocalizedText Strings\\Objects:BankMod.Phone_Desc]"

    2. 新增 Strings/Objects 资产注入：
       if (e.NameWithoutLocale.IsEquivalentTo("Strings/Objects"))
       {
           e.Edit(assets =>
           {
               var data = assets.AsDictionary<string, string>();
               data.Data["BankMod.Phone"] = I18n.Phone_Name();
               data.Data["BankMod.Phone_Desc"] = I18n.Phone_Description();
           });
       }

  技术原理
    - SDV 1.6 的 TokenParser 会在运行时解析 [LocalizedText ...] 令牌
    - Strings/Objects 资产由游戏按当前语言加载，每次访问都正确本地化
    - I18n.Phone_Name() / I18n.Phone_Description() 在 Strings/Objects 注入时调用，
      此时 SMAPI 的 I18n 系统已正确识别当前语言
    - Name 字段保持 "BankMod.Phone"（内部标识符，不显示给玩家）

  本地化审计结论
    - Data/mail 和 Data/Events 也使用 I18n.Get()，但风险较低：
      信件内容在首次阅读后写入 player.mailReceived，后续不再重新渲染
      语言切换不影响已读信件
    - PhoneItem.cs 中 PhoneItem.ObjectData 为残留死代码，不影响运行时

  代码位置
    BankMod.cs OnAssetRequested Data/Objects (~L377), Strings/Objects (~L390)

  27.3 Bug 3 — 公司名意外回退（路线改名后贷款/迁移中的本地化泄漏）

  问题现象
    测试员汇报：CC/Joja 路线完成后公司名在某些操作后回退为原名或变为中文子公司名。

  根因分析（两个子问题）

  子问题 A — 债券转移泄漏本地化名称
    TransferLoansFromDyingCompany 将倒闭公司的贷款转给固定公司时：
      loan.CompanyName = bestFixed.Name;  // ← 可能是中文子公司名
    若 CC 路线已完成，bestFixed.Name 可能是 "皮埃尔子公司"（而非原始英文标识符），
    导致贷款的 CompanyName 被设为中文，写入存档后：
      - 影响贷款查找逻辑（按 CompanyName 匹配）
      - 影响借款上限计算（CalcMaxBorrow 按 CompanyName 统计已有贷款）
      - 跨存档时中文公司名残留

  子问题 B — 已损坏存档无法迁移
    RouteService.KnownTranslations 字典缺少子公司名称映射：
      已有映射：  "JojaMart" ↔ "Pierre's General Store" 等原始名称
      缺失映射：  "皮埃尔子公司" → "JojaMart"
                  "Joja子公司" → "Pierre's General Store"
                  "Pierre's Subsidiary" → "JojaMart"
                  "Joja Subsidiary" → "Pierre's General Store"
    导致 MigrateLoanNames() 无法识别存档中已存在的中文子公司名称，
    已损坏的存档数据无法自动修复。

  修复方案

  子问题 A — 使用 OriginalName 替代 Name
    loan.CompanyName = bestFixed.OriginalName;  // ← 始终为英文原始标识符
    CompanyDefinition.OriginalName 从 config.json 磁盘文件读取，不受路线改名影响。

  子问题 B — 补全 KnownTranslations 映射
    RouteService.KnownTranslations 新增 4 条映射：
      ["皮埃尔子公司"] = "JojaMart"           // CC 路线：Joja → 皮埃尔子公司
      ["Joja子公司"] = "Pierre's General Store" // Joja 路线：皮埃尔 → Joja子公司
      ["Pierre's Subsidiary"] = "JojaMart"       // 英文变体
      ["Joja Subsidiary"] = "Pierre's General Store" // 英文变体
    MigrateLoanNames 现在可以正确映射所有子公司名称回到 OriginalName。

  路线改名机制回顾
    - ApplyRouteEffects 在首次加载或路线事件触发时执行
    - 改名只修改 c.Name（显示名），c.OriginalName 始终保持原始值
    - _originalCompanyNames 备份恢复机制防止跨存档污染（V3.17）
    - 存档隔离：LoadFromSave 从 config.json 磁盘读取原始名，先恢复再应用路线改名

  28.1 Bug 4 — CC路线完成后"双皮埃尔子公司"（c.Name 中文名泄漏导致匹配失败）

  问题现象
    测试员汇报：CC路线完成后，某一时刻出现Joja子公司和皮埃尔子公司两个名字，
    重进存档后变成双皮埃尔子公司。

  根因分析
    LoadFromSave 和 ApplyRouteEffects 将 c.Name 从 "JojaMart" 修改为 "皮埃尔子公司"。
    整个代码库使用 c.Name == ca.CompanyName 匹配公司：
      - CompanyManager.cs SettleDailyInterest: c.Name == ca.CompanyName → 匹配失败
      - LoanService.cs: c.Name == loan.CompanyName → 匹配失败
      - BankMod.cs: c.Name == req.CompanyName → 匹配失败
    而 ca.CompanyName / loan.CompanyName 始终存储英文 OriginalName（如 "JojaMart"），
    导致公司匹配失败，UI 显示异常。

    更严重的是：GMCM 保存时调用 Helper.WriteConfig(_config)，将中文 c.Name
    持久化到 config.json。下次加载时 MigrateOriginalNames 虽然会恢复 Name 为
    OriginalName，但 LoadFromSave 又立即覆盖为中文名，形成循环。

    双皮埃尔子公司的具体成因：当 config.json 被污染后，两个公司的 Name 都可能
    被错误赋值，或 GetDisplayName 的 fallback 分支 `return company.Name` 返回
    残留的中文名。

  修复方案
    彻底停止修改 c.Name。GetDisplayName() 已经根据 OriginalName + 路线状态
    返回正确的本地化显示名，不需要也不应该修改 c.Name。

    具体修改：
    - LoadFromSave：删除 c.Name = RouteDisplayNames[...] 赋值，仅保留 boost 标志设置
    - ApplyRouteEffects：删除 c.Name = RouteDisplayNames[...] 赋值，仅保留 boost 标志设置
    - c.Name 始终等于 c.OriginalName，确保 c.Name == ca.CompanyName 匹配正确
    - GMCM WriteConfig 不再有中文 Name 泄漏到 config.json 的风险

  原则
    c.Name = 稳定标识符（用于匹配、存储、索引）
    GetDisplayName() = UI 显示名（本地化、路线敏感）
    两者职责完全分离，互不干扰。

  代码位置
    RouteService.cs LoadFromSave (L79-90), ApplyRouteEffects (L377-401)

  28.2 Bug 5 — 复利模式与防复利机制冲突（三个子问题）

  问题现象
    复利模式可能导致防复利机制误触发惩罚，防复利机制可能在复利到期日失效。

  子问题 A — 复利到期日竞态条件（严重）

    OnDayStarted 执行顺序（修复前）：
      1. CompoundDaysRemaining 倒计时 → CompoundActiveCompany 清空
      2. SettleDailyInterest → isCompound=false（已清空）→ 复利最后一天无复利利息！
      3. DetectManualCompoundInterest → continue 守卫失效 → 可能误触发防复利惩罚

    修复：将复利倒计时移到 DetectManualCompoundInterest 之后执行。
    新执行顺序：
      1. SettleDailyInterest → CompoundDaysRemaining 仍 > 0 → isCompound=true ✓
      2. DetectManualCompoundInterest → CompoundActiveCompany 仍非空 → continue 守卫生效 ✓
      3. CompoundDaysRemaining 倒计时 → 可能清空 CompoundActiveCompany
         → 若到期，重置滑动窗口 + 清空 ActiveCompany + 启动冷却

  子问题 B — PreviousBaseAmount 在复利期间不更新（严重）

    修复前：DetectManualCompoundInterest 的 continue 跳过了 PreviousBaseAmount 更新。
    复利到期后，delta = BaseAmount - PreviousBaseAmount 包含整个复利期间的累积增量，
    可能产生虚假大正增量，触发防复利惩罚。

    修复：在 continue 分支中仍然更新 PreviousBaseAmount：
      ca.PreviousBaseAmount = ca.BaseAmount;
      continue;

  子问题 C — 复利到期后滑动窗口残留（中等）

    复利期间的 BaseAmount 变化模式与手动复利不同，但滑动窗口中可能残留
    旧的增量数据。复利到期后，这些数据可能参与 peak-break 检测。

    修复：复利到期时重置该公司的滑动窗口：
      RecentPrincipalDeltas = new int[7]
      WindowDayIndex = 0
      HasFirstIncrease = false
      LastPositiveDelta = 0
      WindowPeak = 0
      WindowBreakCount = 0
      PreviousBaseAmount = BaseAmount
